# Step 55 — Audit Integration

## Scope delivered
- Transactional SQLAlchemy audit hooks for `User`, `Role`, `Permission`, and `UserDataScope` create/update/delete operations.
- Before/after field values are captured for updates; sensitive fields (`password`, `password_hash`, `secret`, `token`) are excluded.
- Actor, one active role code, UTC timestamp, request correlation ID, source IP, entity/action/result, and safe context are captured.
- Explicit append-only events cover user-role assignments, role-permission assignments, data-scope revocation, login success/failure, logout, and permission denials.
- Successful business-operation audit rows are inserted in the same SQLAlchemy transaction as the business change. Rollback therefore rolls back the corresponding success audit rows.
- Failed login and authorization-denial events are written in an independent session where configured, so the expected 401/403 rollback does not erase the security event.
- `AuditLogRepository` remains append/query-only; no update/delete API was introduced.

## Important implementation notes
- Audit ORM hooks are enabled when an authenticated request resolves the current user. Login explicitly enables request audit context before authenticating.
- Bulk association-table DML is audited explicitly at the API boundary.
- Request correlation IDs are generated by middleware when absent and propagated to audit context.
- No database schema change or Alembic migration is included; the existing `audit_logs` table is reused.
- Audit failures are logged and should be monitored. For high-assurance production use, ship audit events to a separately protected/immutable store and restrict direct database write permissions.
